P104 Program Report

Bonsai 27B ternary on one NVIDIA P104-100 · 23–24 November 2026 · gpu-host

Goal: make a mining-grade 8 GB Pascal card run a 27B ternary model well enough to serve as a coding agent's inference engine, with long context on the card, at low power, with the model's output statistically unchanged. The work ran as one coordinator plus eleven specialist agents on a serialized GPU queue, every change proven on op tests and logit divergence before it counted.

What was built

  • Ternary decode kernel for sm_61 (program 1): octet geometry, dp4a decode, CUDA graphs, FWHT fusion. 1.65× decode, 2× prefill over the stock fork.
  • Flash-attention decode kernel for Pascal: attention at 61k context from 6.0 to 0.6 ms per layer; decode nearly flat with depth. Gated so its multi-token verify path only engages above 4k context, where it is clean.
  • Prefill tile (+9 % prefill) with a measured dispatch threshold (128 columns) so mid-size verify batches keep the faster older path.
  • Multi-column verify kernel: 2–4 draft tokens now cost 1.04–1.11× one token instead of 1.4–2.7×; drafting at depth 2–3 pays. Plus a bit-identical accumulator trick worth 2–5 % on verify mat-vecs.
  • Device-resident recurrent checkpoint: a 127-line server fix that stops a 150 MiB state copy crossing the Gen1 x2 link on long drafts. Save 389 → 16 ms; +39–41 % on edit turns with partial acceptance; restore path proven, text byte-identical.
  • Model-side decisions, all measured: K/V cache types (q8/q4 best quality per byte, q4/q4 chosen to fit 48k), the thinking-close edit ported byte-exactly onto the serving file, n-gram drafting stacked on the native MTP head, tool calling verified 5/6.
  • Infrastructure: a GPU job queue with session-level cleanup and name-based timeouts, a one-command cut-over between serving and research, a verification battery (op tests, interleaved benches at 0/16k/32k, KL divergence, two serving turns, temp-0 text compare), a 128 W power cap and memory offset applied at boot.

What was ruled out, with data

The single-token decode kernel sits at about 70 % of memory bandwidth, and every structural alternative was built and measured against it: register cap (−1.8 %), persistent grid (−3.5 %), K-split (−18 / −37 %), permute-free decode (−9.5 %), two-deep prefetch (−7 / −14 %), activation-stationary verify (−40 %), direct load without shared memory (±4 %). Probes show a 52 µs compute floor and a 65 µs weight stream that do not overlap; the staging hand-off serializes them and Pascal has no asynchronous copy to break it. Also rejected: GPU-side sampling (no gain with the real sampler), activation sparsity (quality), an attention build without the native mixed-KV instance (slower), 64k context on 8 GB (loads, but no headroom under load).

State at close

  • Serving: bonsai-best.service on gpu-host port 8097, build best8, 48k context, 4-bit caches, draft head + n-gram at depth 3, device checkpoint on, 128 W, memory +100. Health OK, zero restarts since cut-over.
  • Switching: sudo bonsai-queue-resume hands the card to the research queue; sudo bonsai-cutover <bin> brings serving back.
  • Ready but not landed: three bit-identical graph fusions (+1.5 % decode) and a bf16 SSM mat-vec kernel (+2 %, untested on the card); together a best9 worth about +3 % for one build and one 18-minute verification.
  • Open: gpu-host's host RAM (three compilers segfaulted overnight; run a memory test), continuous batching numbers (job hangs client-side), 64k context for Hermes Agent (needs the P40 or two cards; chunked-prefill attention design saved).

Where the next gains are

On this silicon the kernel side is closed. Decode speed now scales with memory bandwidth and tokens per step: the memory clock (clean to +200 in the gated ladder, set conservatively at +100), draft acceptance, and the two small fixes above. For the production box, the same build runs 64k on the P40 or across two P104s with room to spare, and the Hermes requirement is met there.
