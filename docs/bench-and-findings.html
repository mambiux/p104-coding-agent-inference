Longshot Bench

Every candidate for the Pascal coding server got the same brief: build longshot.html, a self-contained showcase page, in one shot. A headless Chromium then opened each page and clicked through it. Nobody shipped a clean page; the table shows who came closest and why.

Verdict. No model under 8 GB produced a bug-free page in a single pass. The closest was Ternary Bonsai 27B PQ2_0 (thinking on, 16k context): correct three-state theming, a drawn chart with axes, legend and hover, task filters, a correct prime finder and the most honest write-up, undone by one DOM call (replaceChild on an emptied list) that hides the task list and, after a reload, takes the prime finder down with it. Qwen3.5-9B looked right on paper but dies at load (draw used before initialization). The 9B ternary models are the fastest by far (71 to 75 tok/s with the MTP head) and the sloppiest.

Update, fix loop. When the browser's errors were fed back, Bonsai 27B repaired everything in a single round (including a bug it was not told about); Qwen3.5-9B needed four rounds to stop crashing and never fixed its wrong answer. See the fix-loop section.

What this means for the server. At this size, intelligence per gigabyte lives in the 27B ternary models, but their thinking must be capped or they burn the whole budget deliberating (Dory 4B and the abliterated 27B-MTP never emitted a page even with 14k tokens). The MTP draft head is worth keeping: it lifted the 27B from 16 to 29 tok/s on this card. The realistic workflow is generate → run → feed errors back → fix; single-shot is not where these models win.

Fix loop: can Qwen3.5-9B repair its own page?

The realistic use of a coding server is not one shot but generate → run → feed the errors back → fix. Qwen3.5-9B Q4_K_M (the model that looked best on paper) got that loop: after each round, Chromium's uncaught errors and the failed requirement checks went back to the model together with its own file, and it returned a full corrected document. Six fix rounds, ~4 min each at 26 tok/s.

Bonsai 27B: clean in one round. Given the same kind of report (its five uncaught errors and the failed checks, nothing more), the 27B ternary model rewrote most of its page and came back with zero errors, a working task list, the correct 10th prime and — unprompted, since the harness never mentioned it — the bar-height bug fixed (fillRect(x, y, BAR_W, h)). It cost one 13-minute round at 15.6 tok/s with a 4k reasoning cap, about the same wall-clock as three Qwen rounds, and ended where Qwen could not get in six.

Qwen3.5-9B: crashes yes, logic no. With the loop, Qwen3.5-9B turned a page that died at load into one with zero runtime errors and every interactive feature working, in four effective fixes. What it could not do, even when told the expected answer (29) four times, was repair an off-by-one in its own prime finder (count = 1; candidate = 3; candidate++ skips 3); from round 4 on it re-emitted the same file unchanged. Crashes it can fix from a stack trace; a wrong answer it cannot see.

Two operational findings for the server. First, uncapped thinking is the failure mode: on round 2 the model spent 9k and then 13k tokens entirely on reasoning and emitted nothing; the upstream llama-server --reasoning-budget 4000 flag fixed that immediately and the later fixes used 0.4–4k characters of reasoning. Second, the harness has to report facts, not guesses: an early version told the model "it answered 11" when the page said 31, which sent a round in the wrong direction.

Final pages: bonsai-fixed.html (round 1) · qwen-fixed.html (round 6). Loop driver: dev-box:~/attic/longshot/fixloop.py.

Kernel work: the same card, 2× prefill and 1.65× decode

Tuning knobs were exhausted (power, clocks, flash-attention, KV type, fusion and FWHT environment switches all moved results by ±2 %), so a four-agent team went after the ternary kernels themselves in the PrismML fork: a researcher, two engineers working independently, and an architect who started from microbenchmarks of the silicon. All GPU runs were serialized through a job queue with a watchdog, and every kernel had to pass the backend op tests and a logit-level comparison before its speed counted.

What was wrong. Three gates in the fork, all read from the source: PTQ1_0 prefill on compute capability 6.1 never used the int8 dp4a tile kernels (it fell back to F32 dequantize + cuBLAS, a 137 tok/s ceiling on this card); CUDA graphs were disabled below Volta (3.9 µs per launch versus 0.97 µs in a graph, at over a thousand launches per token); and the decode kernel's trit recurrence compiled v×3 into emulated 32-bit multiplies — 1,671 XMAD instructions per 256 dp4a — while re-reading activations five times per weight block.

What was built. A Pascal-only one-column PTQ1_0 mat-vec (8-lane groups per two rows, 16-byte coalesced loads staged through shared memory one step ahead, activations kept in registers, and a digit decode written as H(t+1) − 3·H(t) so the masks disappear and the multiply becomes a full-rate add); the existing dp4a MMQ enabled for PTQ1_0 with wider 128-row tiles (11.2 TOPS vs 9.4 at 64); CUDA graphs and the FWHT+q8 fusion enabled for sm_61. Everything is gated to cc 6.1 and switchable off by environment variable.

Correctness. 415/415 PTQ1_0 op tests and 262/262 PQ2_0 op tests pass. Against the reference logits over 1,024 tokens the decode kernel measures mean KL divergence 1.4e-4, top-1 agreement 99.6 %, perplexity ratio 1.0013; the control run with the kernel switched off gives KLD 0 exactly. Temperature-0 text differs from the first token, traced to the prefill path change (int8 MMQ instead of cuBLAS — the path the fork itself calls more accurate), not to the new kernel. An alternative decode kernel from engineer A is bit-exact with the reference at 25.1 tok/s and is kept for reproducibility.

Silicon facts measured on the way (useful for every P104 in the fleet): 15 SMs, not 20; DRAM streaming saturates at 300 GB/s with about 8 KB in flight per SM; dp4a runs at full FP32 rate, shifts and byte-permutes at half rate, popcount at a quarter (so bitplane tricks lose); 32-bit integer multiply is three emulated instructions; shared-memory lookup tables are bandwidth-bound; launches cost 3.9 µs, 0.97 µs inside a graph. Profilers refuse the card ("Crypto Mining Processor"), so all breakdowns came from op-level timing and microkernels.

Real-world check. The Bonsai 27B fix-loop round from the section above (7.8k-token prompt, ~9k tokens generated with a 4k reasoning cap) took 13 m 09 s on the reference build and 6 m 59 s on the merged build — 24.4 tok/s end to end — and still produced a clean page in one round (0 errors, 10th prime = 29).

Left on the table. Mat-vecs now take ~26 of a ~34 ms token; the remaining 8–9 ms is the linear-attention recurrence, attention, norms and quantize steps. A row-interleaved weight repack at load time (same bytes, better coalescing) is worth an estimated +5–8 %; a purpose-built ternary prefill tile could reach ~240 tok/s; PQ2_0 could take the same decode geometry. Power. There is no knee. Context. Only the model's 16 full-attention layers keep a KV cache (the linear-attention layers carry a fixed recurrent state), so the cache is small: ~64 KB per token in f16. q8_0 is numerically free but ~11 % slower at depth on Pascal; q4_0 is the fastest at depth and uses the least VRAM, at the cost of a measurable but small drift (one more Q4-quant step's worth). The honest ladder: 20k f16 for exactness, 40k q8_0 with no quality trade, 48–64k q4_0 for agent work; 64k leaves 228 MiB spare, 48k leaves 650. A cold 60k prompt costs ~7 minutes of prefill on this card; agent turns append, so with prompt caching that is paid once per session. The fill tests settled it: a 60.9k-token prompt at 64k prefilled in 701 s (87 tok/s), generated at 11.8 tok/s, peaked at 7,931 MiB with no allocation failure, answered correctly (it named the actual files and functions in the prompt) and reused the cache on a follow-up turn; a 44k prompt at 48k prefilled in 456 s and generated at 14.8 tok/s with 600 MiB spare. So 64k is stable, but decode at full depth falls from 30.8 tok/s (12k) to 14.8 (44k) to 11.8 (61k) — the cost of the 16 full-attention layers — which is what sets the practical sweet spot for an agent, not VRAM. Both fill runs were done at the 128 W cap now set on the card.
